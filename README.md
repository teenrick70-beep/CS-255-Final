# CS-255-Final
Final Project for CS 255
Project Overview

DriverPass was the client for this project. They wanted a web-based system that would help students prepare for their driving tests through online classes, practice tests, and scheduled driving lessons. The system also needed to support the employees who manage appointments, instructors, vehicles, student progress, and customer information. For Project One, I documented the business requirements based on the client's needs. For Project Two, I used those requirements to create a system design with UML diagrams and technical recommendations.

Reflection
What did you do particularly well?

I think one of the things I did best was taking the information from the client interview and organizing it into clear system requirements. I tried to think about how the system would work for both customers and employees rather than focusing on just one side. For example, I included scheduling rules to help prevent double bookings, as well as different access permissions depending on a user's role. I also felt that using UML diagrams helped me connect the written requirements to the actual design.

What part would you revise, and how would you improve it?

If I could revise one part of my work, I would spend more time refining the UML diagrams. Although they communicate the main processes, I think some of the decision points and alternate outcomes could be clearer. I would especially focus on what happens when an instructor or vehicle is unavailable, or when a customer needs to change an appointment. I would also compare each diagram with the requirements document again to make sure the details stay consistent.

How did you interpret the user's needs and implement them into your design? Why is this important?

I interpreted the users' needs by looking closely at the DriverPass interview and identifying what each type of user needed to accomplish. Customers needed access to learning materials and a way to schedule lessons, while employees needed tools to manage appointments, record progress, and handle administrative tasks. I used those needs to guide the system's features and role-based permissions. I think this step is important because even a well-built system can fall short if it does not solve the problems people actually have.

How do you approach designing software? What strategies would you use in the future?

My approach to designing software is to understand the problem before deciding how the system should work. I would start by gathering requirements, identifying the different users, and separating essential features from technical constraints. From there, I would use diagrams and written documentation to map out how the parts of the system connect. In future projects, I would also ask for feedback earlier and review my designs against the original requirements throughout the process. This would help me catch misunderstandings before they become bigger issues during development.
